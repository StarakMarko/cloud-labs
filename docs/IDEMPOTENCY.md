# Ідемпотентність операцій запису (Idempotency-Key)

## 1. Яку проблему це розв'язує?

Метод `POST` за стандартом HTTP не є ідемпотентним. Якщо клієнт надіслав запит на створення парку, сервер створив запис у базі, але на поверненні відповіді обірвався зв'язок (таймаут Wi-Fi, збій мережі) — клієнт подумає, що сталася помилка, і надішле запит повторно. Без ідемпотентності це призведе до появи двох однакових парків у базі (а в онлайн-магазинах — до подвійного списання грошей).

---

## 2. Як це реалізовано

У `app/server.js` додано middleware `idempotent`:
1. Клієнт передає заголовок `Idempotency-Key: <унікальний_uuid>`.
2. Сервер атомарно пробує записати ключ у Redis: `redis.set("idem:user:key", { state: "processing" }, { NX: true, EX: 86400 })`.
3. Якщо ключ уже існує і має статус `done`, сервер одразу віддає збережену відповідь і додає заголовок `Idempotent-Replayed: true`.
4. Якщо ключ новий, виконується бізнес-логіка, а фінальна відповідь зберігається в Redis на 24 години (TTL = 86400).
5. Якщо трапилась помилка сервера (5xx), ключ видаляється, щоб дозволити повторну спробу.

---


## 3. Поєднання із завданням 6 (черги)

У чергах Amazon SQS діє правило доставки «щонайменше один раз» (at-least-once). Якщо воркер отримає одне й те саме повідомлення двічі через збій підтвердження, перевірка ідемпотентності запобігає повторному `INSERT` у MySQL, гарантуючи рівно одну обробку завдання.
